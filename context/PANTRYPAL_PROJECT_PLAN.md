# PantryPal Product and Engineering Plan

Status: Approved implementation source of truth  
Audience: Product, design, mobile, backend, QA, and deployment agents  
Initial release: Invite-only beta  
Surfaces: Android APK and responsive installable web app  
Last planning revision: 2026-08-15

## 1. Product definition

PantryPal turns recipe links and shared media into reviewed, scalable recipes and a coordinated household shopping plan. Its central promise is:

> Bring a recipe. Choose the servings. Know exactly what the household needs.

PantryPal is not merely a recipe bookmarker. It connects five activities:

1. Importing and validating recipes.
2. Scaling ingredients for a chosen number of servings.
3. Planning cooking and assigning responsibility.
4. Combining requirements into household shopping trips.
5. Preserving a visual history of meals the household cooked.

The initial audience is families, couples, roommates, and other small households that coordinate meals and shopping. The beta is multi-household and multi-tenant from the beginning, even though it will initially run on one privately owned VPS.

### 1.1 Product principles

- Trust before automation: AI output is always a reviewable draft with evidence and uncertainty.
- Explain every failure: error messages name the cause and provide the next useful action.
- Equal household participation: no organizer, shopper, viewer, or cook roles.
- Attribution instead of permission hierarchy: shared changes show who did what and when.
- Mobile first: every primary action works comfortably with one hand and touch input.
- Shopping accuracy over false precision: never invent missing amounts or unsafe conversions.
- Lightweight pantry awareness: track whether planned demand is covered without forcing exact inventory management.
- Historical truth: archived cooking instances retain the values used at the time.

## 2. Scope

### 2.1 MVP outcomes

The MVP is complete when a household can:

- Create accounts and join one or more households.
- Import recipes from supported sources or enter them manually.
- Understand what PantryPal extracted and what remains missing.
- Correct ingredients, quantities, classifications, servings, and instructions.
- Scale a recipe and save it without scheduling it.
- Schedule cooking, identify the responsible cook, and transfer that responsibility with consent.
- Create and confirm shopping dates.
- Automatically or manually associate planned cooking with a shopping trip.
- Aggregate compatible ingredients into a shared list.
- mark items as available, partial, needing recheck, purchased, or ignored.
- See realtime attributed changes and receive assignment/date notifications.
- Browse a visual cooking archive and reuse a past recipe.

### 2.2 Explicitly deferred

- Native iOS distribution. iPhone users use the responsive PWA.
- Retailer ordering, store-specific pricing, coupons, and delivery integrations.
- Nutrition calculations, medical dietary guidance, and allergy guarantees.
- Exact continuous pantry stock depletion.
- Receipt scanning and automatic purchase reconciliation.
- Public social profiles or recipe discovery feeds.
- Payments and subscriptions.
- Hebrew UI, RTL, and multilingual extraction optimization.
- Fully offline conflict resolution.
- Dockerfiles, Compose files, reverse-proxy configuration, TLS, and VPS deployment automation.

## 3. Identity, households, and permissions

### 3.1 Accounts

- Email is the globally unique sign-in identifier and is compared case-insensitively.
- Display names are not unique.
- Passwords must be at least 12 characters and are hashed with Argon2id.
- The beta has no outbound email, email verification, or self-service password reset.
- An operator CLI resets forgotten passwords and revokes every active session for the account.
- An account can belong to multiple households and switch between them.

### 3.2 Invite-only registration

- Creating a new household requires a one-time beta invite generated by an operator CLI.
- A beta invite is stored hashed, expires by default after 14 days, and can be redeemed once.
- Joining an existing household requires its reusable household invite code.
- Household codes contain at least 72 bits of entropy, are shareable as text or QR, and can be rotated by any active member.
- A signed-in account can join another household with its code.

### 3.3 Equal permissions

There are no household roles. Every active member can:

- Import, create, edit, archive, restore, and reuse recipes.
- Create, edit, confirm, start, complete, or cancel shopping trips.
- Add or remove recipe requirements from a trip.
- Update pantry and shopping item states.
- Schedule cooking and propose cook reassignment.
- Invite new household members or rotate the invite code.
- Change shared household preferences.

Membership security is narrower:

- Members can leave a household themselves.
- Members cannot remove another member in the MVP.
- The operator handles abusive or inaccessible memberships.
- Account credentials and sessions remain personal.

Shared destructive actions use confirmation, soft deletion for 30 days, and an undo action where practical.

### 3.4 Attribution

Every shared mutation records:

- Immutable actor account ID.
- Actor display name snapshot.
- Household ID.
- Entity type and entity ID.
- Action type.
- Safe before/after summary.
- Timestamp.

Activity records remain until the household is deleted. A later display-name change does not erase historical identity. Duplicate display names are distinguished by avatar/color and email in member-selection interfaces.

## 4. Core user journeys

### 4.1 Import and review

1. A member pastes a link, shares text, or uploads media/screenshots.
2. PantryPal validates the input and shows live analysis stages.
3. The backend extracts deterministic data before invoking AI.
4. The review screen displays the structured recipe, evidence, classifications, and completeness.
5. The member corrects uncertain or missing values.
6. The member saves it to the library, starts Quick Cook, schedules it, or adds it to a trip.

### 4.2 Quick Cook

Quick Cook supports a recipe with no cooking date or shopping trip:

- Choose target servings and see scaled quantities immediately.
- Save the recipe to the library.
- Optionally use Mark cooked now to create an archive entry for today.
- Later add the saved recipe to any cooking date or shopping trip.
- Do not affect a shopping list until a trip association is made.

### 4.3 Plan and shop

1. A member schedules a recipe and becomes its confirmed cook.
2. PantryPal recommends the latest confirmed trip occurring on or before the cooking date.
3. The member can override the trip or leave it unassigned.
4. Recipe requirements aggregate with other recipes assigned to that trip.
5. Household members check what is already available.
6. The shopping list updates in realtime while shopping.

### 4.4 Cook handoff

- The member who creates a cooking instance is the accepted cook by default.
- Reassigning it creates a Pending transfer.
- The existing cook remains responsible while the target decides.
- Accepting transfers responsibility.
- Declining leaves the existing assignment unchanged.
- Any later transfer uses the same protocol.
- Proposals, acceptances, declines, and cancellations create activity events and push notifications.

### 4.5 Archive and reuse

- After a cooking date passes in the household timezone, PantryPal assumes the meal was cooked.
- The cooking instance becomes an immutable archive snapshot.
- Selecting Cook again creates a new cooking instance rather than modifying history.
- The new instance can use a new serving target, cooking date, cook, or shopping trip.

## 5. Recipe ingestion

### 5.1 Supported launch inputs

- Ordinary public recipe webpages.
- Public YouTube videos.
- Public Instagram posts and Reels.
- Public TikTok posts.
- Pasted recipe text or caption text.
- Uploaded screenshots or images.
- Uploaded video or audio files.

Private, removed, expired, paywalled, login-only, geographically restricted, or technically blocked content cannot be guaranteed.

### 5.2 Adapter contract

Each URL platform implements the same conceptual interface:

- probe: validate the host, canonicalize the URL, identify content ID, and determine public availability.
- fetchMetadata: obtain title, caption/description, author attribution, thumbnail, and accessible comments.
- acquireMedia: optionally obtain a bounded temporary local media file.

Adapters are provider-neutral so official APIs, open-source tools, or a paid provider can be replaced without changing recipe extraction.

### 5.3 Source-specific policy

#### Webpages

1. Fetch through an SSRF-protected HTTP client.
2. Prefer Schema.org Recipe JSON-LD and other structured recipe markup.
3. Parse useful page text, headings, lists, tables, and hero images.
4. Use Gemini only for unresolved structure or ambiguous content.

#### YouTube

1. Resolve public metadata and accessible description/comments.
2. Pass public YouTube URLs directly to Gemini when supported.
3. Use media acquisition only when a local asset is required for frame selection or the direct path fails.

#### Instagram and TikTok

1. Probe official public embed/oEmbed metadata first.
2. Analyze accessible caption/title text before downloading media.
3. Put yt-dlp behind SOCIAL_MEDIA_DOWNLOAD_ENABLED.
4. Permit gallery-dl as a secondary feature-flagged adapter for applicable image/carousel sources.
5. Never request or store a household member's social-media cookies.
6. Treat unofficial extraction as best effort, not a guaranteed platform contract.
7. Always offer paste, screenshot, upload, and manual fallbacks.

### 5.4 Cost-aware multimodal pipeline

Use the following order and stop as soon as the recipe is sufficiently supported:

1. Structured webpage data.
2. Page text, title, caption, description, and accessible comments.
3. Gemini structured extraction from collected text.
4. Temporary media acquisition when required.
5. FFmpeg audio extraction to mono 16 kHz FLAC.
6. Gemini 2.5 Flash audio analysis with timestamps and structured output.
7. A vision pass when:
   - Completeness is below 75%.
   - No explicit amount exists for any required ingredient.
   - The audio indicates on-screen quantities or silent preparation.
   - Speech is absent or unusable.
8. Sample scene changes, likely text frames, and the final 20% of the video.
9. Escalate to a compressed video-only Gemini pass only when sampled frames remain insufficient and the media is within configured limits.

Default safeguards:

- Maximum source video duration: 30 minutes.
- Maximum acquired file size: 500 MB.
- Full video escalation limit: 10 minutes and 200 MB before compression.
- Maximum sampled frames per visual pass: 16.
- Temporary local media TTL: 60 minutes.
- Gemini remote files are deleted after the import completes or fails.
- All limits are environment-configurable and enforced before expensive processing.

### 5.5 Import job stages

- QUEUED
- VALIDATING_SOURCE
- FETCHING_METADATA
- FETCHING_CONTENT
- ANALYZING_TEXT
- ACQUIRING_MEDIA
- ANALYZING_AUDIO
- ANALYZING_VISUALS
- STRUCTURING_RECIPE
- READY_FOR_REVIEW
- FAILED
- CANCELLED

The app shows determinate stage progress when known and stage-level progress otherwise. Jobs can be polled and also publish Socket.IO updates.

### 5.6 Extraction schema and evidence

The Gemini response must validate against a versioned schema containing:

- Recipe title.
- Source attribution and canonical link.
- Original serving yield and yield wording.
- Ingredients with minimum/maximum quantity, original unit, normalized unit, preparation note, classification, and shopping inclusion.
- Ordered preparation instructions.
- Field confidence.
- Evidence origin and excerpt, timestamp, or frame reference.
- Detected language.
- Recipe-present and visual-dependency signals.

Values without evidence are marked inferred. An inferred quantity cannot become shopping-ready until manually confirmed.

## 6. Completeness and review

### 6.1 Segmented completeness meter

The review header displays three segments:

- Automatically extracted.
- Manually supplied or corrected.
- Still missing.

Required-field weights:

- Title and source: 5%.
- Original serving yield: 20%.
- Required ingredient names: 25%.
- Scalable required quantities and units: 40%.
- Usable instructions: 10%.

Ingredient-level weights are divided evenly among required shopping ingredients. Flexible ingredients, garnishes, pantry staples, oils, and spices excluded from shopping are removed from the missing-value denominator when their amount is absent.

Manual corrections move weight from Missing or Extracted to Manual; they never masquerade as AI extraction.

### 6.2 Readiness states

- Draft: can be saved and viewed.
- Cook-ready: contains enough information for the user to follow or interpret it.
- Shopping-ready: original servings are known and every required shopping ingredient has a usable amount and compatible unit/count.
- Needs review: contains unresolved required shopping information.

A Needs review recipe may be scheduled with a prominent warning, but it cannot silently contribute incomplete data to a shopping trip. Its planned instance remains flagged until corrected.

### 6.3 Ingredient classes

- REQUIRED: affects readiness and shopping by default.
- FLEXIBLE: wording such as to taste or as needed is valid.
- PANTRY_STAPLE: salt, pepper, common oils, and similar items; excluded from missing-amount penalties.
- GARNISH: optional and excluded from shopping by default.

Users may change classifications and shopping inclusion. That manual decision becomes part of the recipe version.

## 7. Error behavior

Every error includes a plain-language title, cause, channels checked, and recovery actions.

| Code | Meaning | Recovery |
|---|---|---|
| SOURCE_UNAVAILABLE | Link cannot be reached | Retry or check the URL |
| SOURCE_PRIVATE_OR_LOGIN_REQUIRED | Content needs login or is private | Paste text, upload media, or enter manually |
| SOURCE_REMOVED | Platform reports missing content | Choose another source |
| SOURCE_UNSUPPORTED | Host or content type is unsupported | Paste or upload |
| SOURCE_BLOCKED | Page blocks safe analysis | Paste text or screenshots |
| SOURCE_METADATA_ONLY | Only title/caption metadata was accessible | Upload media or continue manually |
| PROVIDER_RATE_LIMITED | Platform or AI provider throttled the request | Retry at the displayed time |
| MEDIA_TOO_LARGE_OR_LONG | Configured safety limit was exceeded | Upload a shorter clip or paste text |
| MEDIA_PROCESSING_FAILED | Download, probe, audio, or frame processing failed | Retry or use a manual fallback |
| RECIPE_NOT_FOUND | No recipe was found in accessible channels | Choose another link or create manually |
| INGREDIENTS_NOT_FOUND | A recipe-like item had no ingredient list | Enter ingredients manually |
| SCALABLE_AMOUNTS_NOT_FOUND | Ingredients exist but no usable required quantities exist | Fill amounts manually |
| SERVING_YIELD_MISSING | Ingredients were found but original servings are unknown | Enter the original yield |
| EXTRACTION_SCHEMA_INVALID | AI output failed validation | Automatic retry, then manual fallback |
| ANALYSIS_FAILED | Unexpected import failure | Retry with preserved user input |

Missing amounts for optional spices, oils, garnishes, or flexible ingredients do not produce an error.

## 8. Scaling and unit normalization

- Store quantities as decimal minimum/maximum values, never binary floating point.
- Preserve the original text and unit alongside normalized values.
- Scale using target servings divided by original servings.
- Scale quantity ranges at both ends.
- Display kitchen-friendly fractions where unambiguous while retaining exact stored decimals.
- Metric is the household default.
- Allow common mass, volume, and count conversions within the same dimension.
- Do not convert volume to mass without a verified ingredient-specific density rule.
- Package, bunch, clove, can, and similar units remain semantic counts.
- Merge ingredients only when canonical identity and unit dimensions are compatible.
- Keep cheeses, flours, oils, and other materially distinct varieties separate unless the user explicitly merges them.
- Tapping an aggregated item reveals each recipe contribution.

## 9. Planning and cooking dates

### 9.1 Cooking instances

A cooking instance contains:

- Recipe version snapshot.
- Cooking date or null.
- Target servings.
- Scaled ingredient snapshot.
- Linked shopping trip or null.
- Assignment mode: AUTOMATIC or MANUAL.
- Current confirmed cook.
- Pending target cook, if any.
- Source and archive cover snapshot.
- Creator and timestamps.

Library recipes have no cook assignment. A cook assignment begins when a recipe is scheduled, added directly to a trip, or marked cooked now.

### 9.2 Automatic trip assignment

- Select the latest Confirmed shopping trip whose date is on or before the cooking date.
- Show the suggested assignment before saving.
- Allow any member to override or clear it.
- Automatic assignments may be recalculated when trip dates change.
- Manual assignments are never silently moved.
- If no valid trip exists, show Needs shopping trip.

## 10. Shopping trips and pantry awareness

### 10.1 Trip lifecycle

- PROPOSED
- CONFIRMED
- IN_PROGRESS
- COMPLETED
- CANCELLED

Any member can create, edit, or confirm. Editing the date of a Confirmed trip returns it to Proposed and records who changed it. Ingredient additions do not unconfirm the date, but they may invalidate pantry confirmations.

### 10.2 Shopping item states

- NEED_TO_BUY
- CONFIRMED_AT_HOME
- CHECK_AGAIN
- PARTIALLY_AVAILABLE
- PURCHASED
- IGNORED

Each pantry confirmation stores:

- Member and timestamp.
- Optional known amount and unit.
- Total planned demand at confirmation time.
- Cooking/trip horizon covered.

Rules:

- If availability was recorded only as enough and demand increases, switch to Check again.
- If an exact compatible quantity still covers increased demand, keep Confirmed at home.
- If it covers only part, switch to Partially available and compute the remainder.
- When the related cooking date passes, mark the assessment stale for future plans.
- Purchased is trip-specific and does not automatically claim exact pantry inventory.
- Adding another recipe requiring the same ingredient immediately reevaluates the state.

## 11. Archive

- A scheduled instance moves into archive after its cooking date is earlier than today in the household timezone.
- The transition assumes cooked; there is no overdue confirmation gate.
- Mark cooked now archives explicitly on the current date.
- A catch-up job archives missed dates after worker downtime.
- Archive is grouped into month grids.
- A date with cooking history uses a circular collage of up to four cover images, an overlaid date number, and a +N badge.
- Opening a date shows all cooking instances and their historical details.
- Preferred cover selection:
  1. Gemini-selected finished dish from ending/scene frames.
  2. Source recipe hero image.
  3. Platform thumbnail.
  4. Branded PantryPal placeholder.
- Store final covers as optimized WebP in MinIO.
- Cook again always creates a new instance.

## 12. Activity and notifications

### 12.1 In-app activity

The activity inbox receives:

- Recipe imports, edits, and deletions.
- Cooking creation, date changes, and archive transitions.
- Cook reassignment, acceptance, and decline.
- Shopping trip proposals, edits, confirmations, and completion.
- Pantry confirmations invalidated by new demand.
- Household joins, leaves, invites, and code rotations.

Do not notify the actor about their own routine mutation. Use deduplication keys so retries cannot create duplicate notifications.

### 12.2 Background push

- Android uses Firebase Cloud Messaging.
- Web uses VAPID Web Push and a service worker.
- Push notifications always have a matching in-app record.
- Request permission contextually, not on first launch.
- Required push cases: cook assignment/response, shopping-date confirmation/change, upcoming confirmed trip, and pantry recheck caused by new demand.
- Push payloads contain identifiers and safe summary text, never full ingredient or account data.
- Deep links open the affected household and entity.

## 14. Visual and interaction system

### 14.1 Direction

PantryPal uses a playful-family style that remains suitable for adults:

- Flat, colorful surfaces instead of glass or heavy shadows.
- Friendly rounded geometry and simple food/pantry illustrations.
- Clear hierarchy and restrained information density.
- No emoji as structural icons.

Starting tokens:

- Primary terracotta: #9A3412.
- Action green: #059669.
- Cream background: #FFFBEB.
- Primary foreground: #0F172A.
- Supporting produce colors may use gold, berry, and aubergine only after contrast validation.
- Heading typeface: Baloo 2.
- Body typeface: Nunito Sans.
- Spacing: 4/8dp scale.
- Touch targets: at least 48x48dp.
- Corners: a consistent small/medium/large radius scale.
- Motion: 150-250 ms for normal feedback, interruptible and reduced-motion aware.

Create paired light and dark semantic tokens. Never hard-code raw colors inside feature widgets.

### 14.2 Signature elements

- Segmented extraction completeness bar at the top of recipe review.
- Clear source/evidence chips for extracted fields.
- Ingredient state combines icon, text, and color.
- Archive date collages use readable number overlays and accessible text alternatives.
- Cook cards distinguish confirmed and pending responsibility without relying only on color.
- Provisional app icon: a rounded pantry cupboard whose negative space suggests a spoon or leaf.

### 14.3 Accessibility

## 17. Security and privacy

- Access tokens expire after 15 minutes; refresh sessions expire after 30 days and rotate.
- Store refresh token hashes, not raw tokens.
- Web refresh uses Secure, HttpOnly, SameSite cookies and CSRF protection.
- Android refresh credentials use secure storage.
- Exact-origin CORS and a restrictive web CSP.
- Rate-limit registration, login, code redemption, import creation, media acquisition, and AI calls.
- Scope every query by authenticated membership and household ID.
- Validate redirects and DNS results; reject loopback, private, link-local, metadata-service, file, and non-HTTP(S) destinations.
- Revalidate resolved IPs after redirects to prevent DNS rebinding.
- Never compose media tool calls through a shell.
- Verify MIME, codec, duration, and size with FFprobe.
- Use unpredictable OS temporary directories and cleanup in finally blocks.
- Run a TTL sweeper for abandoned media.
- Do not persist raw social video, audio, full comments, expiring CDN URLs, or unrelated usernames.
- Validate Gemini output against the versioned schema and reject extra/unexpected fields.
- Log identifiers and error codes without secrets or raw private content.
- Secrets remain in ignored environment files; commit only .env.example.

### 19.2 Development process

The user supplies local PostgreSQL, Redis, and MinIO containers. Use conventional configurable ports:

- PostgreSQL: 5432
- Redis: 6379
- MinIO API: 9000
- MinIO console: 9001

Run application code directly:

- NestJS API through an npm development script.
- NestJS worker through a separate npm development script.

## 22. Definition of done

The invite-only MVP is done only when:

- All required flows work on Android and responsive web/PWA.
- The server, worker, Flutter tests, contract drift check, and acceptance suite pass.
- No unresolved cross-household authorization defect exists.
- Import failures are specific and recoverable.
- Temporary media cleanup is verified.
- Shopping totals expose their recipe contributions.
- Cook responsibility cannot transfer without acceptance.
- Archive history remains stable after recipe edits.
- Accessibility and design evaluation gates pass.
- A debug and release-mode APK build succeeds.
- A production-mode Flutter web build succeeds.
- Local run documentation is sufficient without Docker repository files.
- Missing external credentials are the only acceptable reason for skipped live-provider smoke tests.

## 25. Fixed assumptions

- PantryPal is the working name pending later trademark, domain, and app-store checks.
- English is the launch language.
- Metric-first display is the default while original quantities remain visible.
- Gemini 2.5 Flash is the configured default, not a hard-coded permanent dependency.
- Instagram/TikTok downloading is explicitly feature-flagged.
- Scheduled cooking is assumed completed after its date passes.
- Equal content permissions do not imply control over another member's account.
- Push uses FCM on Android and Web Push on browsers.
- The MVP requires a network connection.
- Docker-based VPS deployment is planned but not implemented in this phase.
